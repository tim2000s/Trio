# Boost-in-Trio — Safety & Correctness Audit (2026-06-28)

Scope: the Boost contribution only (BoostV5Core package + Trio app integration + Boost
settings UI + build/signing config). Method: 6-dimension multi-agent review, every finding
adversarially verified (dosing-safety findings by 3 independent lenses). 27 agents.

**Bottom line: build & signing are clean; no crashes or data leakage in Boost code. But it is
NOT yet "fully safe to use" for live automated dosing** — the Active-mode SMB override silently
bypasses several of Trio's stock SMB safety limits (finding D1). Bounded by maxIOB and the
per-shot caps, so not unbounded, but the gaps should be closed before real-world use.

---

## Clean (verified, no issues)

- **Build / signing**: `Config.xcconfig` `##TEAM_ID##` is the standard user-override placeholder
  (documented `ConfigOverride.xcconfig` include); bundle-id / app-group formats correct;
  `Trio.entitlements` sane. No hardcoded developer-specific values.
- **Data leakage**: no secrets, API keys, emails, hardcoded `/Users/...` paths, or embedded
  patient data in Boost source. Real-data fixtures (`Fixtures/*.ndjson`) correctly gitignored.
- **Crashes**: no `try!` / force-unwrap / `fatalError` / `assertionFailure` reachable on real
  data in Boost code. (The keychain crash seen at launch was core-Trio + the unsigned dev build,
  not Boost.)

## Confirmed findings (7)

### D1 — Active-mode SMB override bypasses stock SMB caps  ·  MEDIUM  ·  3/3 verified
`Trio/Sources/APS/OpenAPSSwift/OpenAPSSwift.swift:154-155`
(found independently by two dimensions — same root issue)

In Active mode the engine output is written straight onto the determination:
`det.units = Decimal(result.decision.finalDose)`. This **replaces** the stock SMB that
determine-basal had already (a) clamped to the per-SMB size limit `determineMaxBolus`
(`currentBasal * maxSMBBasalMinutes / 60`) and (b) gated by the user's **SMB Interval**. The
override is unconditional (`if microBolusAllowed, !asleep`; `microBolusAllowed` is hardcoded
true). `finalDose` is bounded only by confirmed/committed caps (default 2.5U, UI up to 7.5U),
the 2.5×insulinReq spike cap, and maxIOB headroom — **not** by `maxSMBBasalMinutes`. Downstream,
`APSManager.performBolus()` enacts automatic SMBs with **no `maxBolus` clamp** (unlike the manual
`roundBolus()` path which does `min(rounded, maxBolus)`).

Net effect: a single automated Boost SMB can exceed the user's configured per-SMB size limit and
can fire every ~5-min loop even when SMB Interval is set higher.

Fix: after computing `finalDose`, re-clamp to the stock SMB cap (`determineMaxBolus`) and respect
the SMB interval (only override when `lastBolusAge > smbInterval`, or reduce to the remaining
interval budget); add a `maxBolus` safety clamp in `performBolus()` mirroring `roundBolus()`.

### D2 — Auto-config 60-min cumulative SMB cap is computed but never enforced  ·  LOW  ·  3/3
`BoostPort/BoostV5Core/Sources/BoostV5Core/BoostV5AutoConfig.swift:105`

`cumulativeSmbCap60MinU` (AAPS's dose-*frequency* safeguard) is produced but never written or
read: `maybeAutoConfigureBoostV5` doesn't persist it, and `V5Inputs`/the engine have no
cumulative-SMB field (comment admits "No Trio engine knob yet"). Combined with D1 (interval also
bypassed), nothing enforces a rolling 60-min delivered-SMB volume limit. A rolling total
(`recentSmbUnits60m`) is already computed in `OpenAPSSwift.swift:117-119` — plumb it in and clamp
`finalDose` to `max(0, cap - recentSmbUnits60m)`.

### D3 — BoostV5Store lock doesn't make load→modify→save atomic  ·  MEDIUM  ·  verified
`BoostPort/BoostV5Core/Sources/BoostV5Core/BoostV5Store.swift:25-27, 43-56`

The comment claims the NSLock guards load→modify→save, but `loadState()` and `saveState()` each
take/release the lock independently; the read-modify-write spans both with no lock held
(`BoostV5Adapter.run`: load@169 → engine → save@215). Reachable overlap: the scheduled
`loop()` (serialized by `loopGuard`) vs `determineBasalSync()` after a manual bolus (not
serialized) can run `BoostV5Adapter.run` concurrently → last-writer-wins. A CONFIRMED meal
hypothesis written by one cycle can be erased by the other, after which the next cycle re-confirms
and can **fire the CONFIRMED-state SMB twice for the same meal**; or a lost `lastRunMs` spuriously
triggers the >30-min meal-hypothesis reset.

Fix: a single lock-held `mutateState { inout … }` API (decode→closure→encode→write in one critical
section), or route all Boost determine work through one serialization point.

### D4 — BoostMealTimeStore.recordConfirmed non-atomic despite "thread-safe" claim  ·  LOW
`Trio/Sources/APS/OpenAPSSwift/Boost/BoostMealTimeStore.swift:16-35`

Same defect class as D3: `history = MealTimeLearner.record(history, …)` is a locked read then a
separate locked write. Concurrent calls can drop a committed meal-time event, skewing the learned
meal-time clustering that drives the anticipatory pre-meal low-target. Lower impact (skews a
learned 60-day target, not an immediate SMB). Fix: lock-held mutate helper.

### D5 — Meal-score ML-dropout renormalizer inconsistent with weight sum  ·  LOW
`BoostPort/BoostV5Core/Sources/BoostV5Core/MealSignalScore.swift:4-16, 50-72`

The seven meal-signal weights sum to **1.07**, not 1.0. When the ML meal model is unavailable
(≥3 cycles), the score is renormalized by `1/(1-0.20)=1.25` — the correct neutralizer for the
actual sum is `1.07/0.87≈1.23`. The 1.25 factor over-inflates the no-ML score by ~1.6%, biasing
the meal hypothesis toward earlier CONFIRMED (thresholds 0.44/0.55) — i.e. slightly more
aggressive dosing, precisely on the degraded path. Fix: use a real `totalWeight` constant, or
normalize the seven weights to sum to 1.0. Verify against the AAPS Kotlin source whether the
1.07/1.25 pairing is an intentional port of the same quirk; if so, document it.

### D6 — Boost dosing-cap prefs not range-validated on decode  ·  LOW
`Trio/Sources/Models/Preferences.swift:455-484`

`Preferences.init(from:)` decodes `boostV5ConfirmedCapU`/`CommittedCapU`/`Aggression`/etc.
verbatim with no clamp. The sliders clamp in the UI, but an imported/remote/corrupted prefs JSON
bypasses the UI, and the engine reads the raw value (`OpenAPSSwift.swift:139`). A cap above the
7.5U UI ceiling would be honored (still bounded by maxIOB). Consistent with how other Trio prefs
decode, but for a dosing-magnitude cap, clamp defensively after decode.

## Verified-dismissed (false positives — checked and cleared)

- **Confirmed/Committed caps don't bound IDLE/OBSERVING/RECOVERING** — dismissed: IDLE dose is
  budget(≤1.2×insulinReq) × actionMult(1.0) × velocity(≤1.0), so the 2.5×spike cap never binds
  there; bounded by maxIOB. The headline "2.5×insulinReq uncapped" misread the math.
- **30-min short-horizon low-glucose gate misses lows at 35-60 min** — dismissed 2/3: whenever the
  full-horizon minGuard < threshold, stock's `lowGlucoseSuspend` early-exits *before* computing
  insulinReq, leaving `insulinReq=0` → `baseInsulinReq=0` → `finalDose=0`. **Note: one of three
  verifiers rated this a real MEDIUM hypo-risk** (Boost override only checks global
  `microBolusAllowed`, not per-cycle `smbIsEnabled`). Worth a second look as defense-in-depth even
  though the majority cleared it.
- **Missing IOB defaults to 0 (opens IOB gates)** — dismissed: nil-IOB is structurally coupled with
  nil/zero insulinReq, so finalDose is 0 regardless. Cosmetic only.
- **First-activation auto-config raises caps without confirmation** — dismissed: intentional,
  bounded ([0.25,2.5] for committed), seeded from the user's own dosing history, one-time, and
  reversible. A one-time "auto-configured" notice would be a nice UX touch.

## Recommended priority

1. **D1** (clamp Active-mode override to maxSMB + interval; add maxBolus clamp in performBolus) —
   the one real gate before live use.
2. **D3** (atomic mutate for persisted state) — prevents double-dose-for-one-meal under overlap.
3. Re-examine the dismissed hypo-gate item as defense-in-depth.
4. D2, D4, D5, D6 — correctness/robustness hardening.
